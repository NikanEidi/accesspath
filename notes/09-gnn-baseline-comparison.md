# 09 — GNN vs. baseline on Clearwell (and two real bugs the result exposed)

## The plan

Convert Riverside District's edges to a line graph (`nx.line_graph`), build a hand-rolled 2-layer GCN in plain PyTorch (no PyTorch Geometric — lighter install, and I wanted to actually implement the message-passing math myself rather than call a library black box), train it on a geographic train/test split, and compare it against the Module 6 baseline (`RandomForestClassifier`) on the exact same split.

## The GCN layer

```python
class GCNLayer(nn.Module):
    def __init__(self, in_features, out_features):
        super().__init__()
        self.linear = nn.Linear(in_features, out_features)

    def forward(self, features, A_norm):
        neighbor_avg = A_norm @ features
        return self.linear(neighbor_avg)
```

`A_norm` is the line graph's adjacency matrix with self-loops added (`A + I`) and row-normalized (divided by each node's degree) — so `A_norm @ features` really does compute "this node's own features, averaged together with its neighbors'." Two of these layers stacked (with a `ReLU` in between) make the model. Training uses ordinary PyTorch: `loss.backward()` + `optimizer.step()`, with the loss computed only on a `train_mask` subset of a graph the model can still see *in full* — masking, not physically splitting the graph into two pieces, which would have deleted real cross-boundary edges and corrupted the neighbor structure for the remaining nodes.

## Bug #1: a checkerboard pattern is adversarial for a GNN

Riverside's original design (notes/08) alternated accessible/inaccessible in a checkerboard (`(r + c) % 2`). First GNN run: **10% accuracy**, identical for both the GNN and the baseline on a *different* split — i.e. a systematic bug, not noise.

The real cause: Riverside's label was generated by a strict column rule (`c < 3` = accessible), and the train/test split was *also* done on `x` (which tracks column). That means train ended up almost entirely one class and test almost entirely the other — both models simply learned to always predict the dominant *training* class, which happened to be the minority class in *test*. This is a real, general ML trap: **if the split variable correlates with the label-generating process, the split isn't a fair held-out test — it's a distribution shift.** Fixed by splitting on `y` (row) instead, since the label rule never depends on row.

## Bug #2: the checkerboard itself was wrong for a different reason

Separately, before that split bug was even found, the checkerboard pattern meant every edge's direct graph-neighbors had the *opposite* label (adjacent cells in a checkerboard always differ). A GCN layer averages neighbor features — doing that on strictly alternating labels actively **cancels the useful signal** instead of reinforcing it. This is a known real limitation of plain neighbor-averaging GNNs: they assume *homophily* (similar things connect to similar things), and a checkerboard is the opposite (*heterophily*).

Redesigned Riverside as **geographic clusters** instead: west half (`c < 3`) accessible, east half not — same 50/50 balance, but now genuinely homophilic (neighbors mostly share labels, matching how real accessible/inaccessible areas actually tend to cluster). Also decoupled `surface` from being a perfect 1:1 proxy for the label (flipped at the two boundary columns), so the task isn't a trivial lookup for either model.

## The honest final result

With both bugs fixed and a fixed random seed (`torch.manual_seed(42)`, for reproducibility — matching the `random_state=42` already used on the baseline):

```
GNN:      accuracy 0.65   (recall on class 0 was weak: 0.22)
Baseline: accuracy 0.67
```

Before fixing the seed, an earlier unseeded run showed the GNN ahead (0.75 vs 0.67) — tempting to report, but not an honest comparison, since PyTorch's `nn.Linear` initializes with random weights every run and that one result could easily have been a lucky draw. **With a fixed seed, the two models are genuinely close — the GNN does not clearly beat the baseline on this dataset.** That's a fair, defensible conclusion: on a small graph (98 labeled edges) with reasonably informative individual-edge features, a simple non-graph baseline can be competitive with a 2-layer GCN. The real advantage of graph structure likely shows up more on larger, less individually-informative data — which is itself a useful, honest finding, not a disappointing one.

## Takeaway

- A result that looks great on one run can just be luck — always fix a random seed before claiming a comparison is real.
- A train/test split must be checked against *why* the labels vary, not just applied mechanically — the same variable can't drive both the label and the split without creating leakage/distribution-shift.
- GNNs are not automatically better than simpler baselines; they depend on the graph actually having exploitable neighborhood structure (homophily) for the task at hand.
